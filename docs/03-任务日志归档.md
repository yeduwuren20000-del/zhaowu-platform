## 二、用户需求原文（第六阶段）

> 开始第六阶段：服务生命周期时间线。基于现有项目聚合模型增加事件记录能力。目标是记录服务状态变化，而不是高频采样。仅在状态变化、端口变化、发现新服务、冲突、SSH/Docker 状态变化时产生事件。
> 新增 eventService 和 eventStore。事件类型包括 started、stopped、crashed、recovered、new_service_found、port_conflict、docker_changed、ssh_offline 等。
> 每个事件必须关联 projectId/serviceId/serverId（存在时），并保留事实字段，例如 PID、端口、进程名、时间戳、来源。
> 不记录每秒状态快照，避免数据膨胀。
> 页面增加：1. 项目详情页最近事件时间线；2. 首页最近活动列表；3. 支持按项目、服务器、事件类型过滤。
> 保持现有 services/routes/store 分层。第一版继续使用 JSON 持久化，不引入数据库。
> 增加事件生成测试，覆盖启动、停止、新端口发现、冲突、SSH失败、Docker状态变化，并保证前五阶段449项测试全部回归通过。

## 三、需求要点（约束）

- **只记变化，不记快照**：状态指纹去抖，PID 不参与指纹（进程重启不算状态变化）；首次观察只建基线，不把现状重放成「刚刚变化」。
- **事件类型**：十种（开始运行 / 已停止 / 异常退出 / 恢复运行 / 发现新服务 / 端口冲突 / 端口变化 / SSH 在线 / SSH 离线 / Docker 变化）。
- **事实字段**：`projectId` / `serviceId` / `serverId` + 端口、PID、进程名、监听地址、退出码、时间戳、来源。
- **分层**：沿用 services / routes / store 分层；JSON 持久化；不引入数据库。
- **旁路**：事件记录失败不能影响启停 / 扫描 / 采集主流程。
- **回归**：前五阶段 449 项断言必须全部通过。

2. **写后端事件层**：新增 `store/eventStore.js`（`data/events.json` 读写）、`services/eventService.js`（事件类型表、状态指纹去抖、四类观察器）、`routes/events.js`（`GET/DELETE /api/events`、`GET /api/events/types`）。
3. **接线**：在项目状态、端口冲突、自动发现、SSH/Docker 采集处挂观察器，记录事件。
4. **修复一处自引入的不一致设计**：把 eventStore 恢复为与 eventService 及已接线一致。
5. **验证**：前五阶段 449 项回归通过后，写事件生成测试。
6. **修复冲突路径缺陷**：全新服务器端冲突只建基线、从不宣告，补上。
7. **写前端**：`components/EventTimeline.jsx`、`pages/Timeline.jsx`（路由 `/timeline`）、`styles/timeline.css`、`api/client.js` 增加 `timeline` 接口。
