# 开发与服务器管理工作台 — 技术方案（第一阶段 MVP）

> 目标：打开一个本地页面，就能一眼看清「哪个项目在运行 / 用了什么端口 / 对应什么 APP 与服务 / 文件在哪 / 本地还是服务器 / 服务器上的部署路径在哪」，并且能直接启动、停止、重启、打开网页、打开目录、看日志。

## 1. 技术选型（简单、稳定、易维护）

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | React 18 + Vite（纯 JSX，不上 TypeScript） | 开发热更新快，构建产物由后端直接托管，零额外部署成本 |
| 后端 | Node.js + Express（ES Module） | 与前端同一套语言；Windows 下调用 PowerShell / taskkill 做进程与端口管理最省事 |
| 持久化 | JSON 文件（原子写入：临时文件 + rename） | 第一版数据量极小（几十条记录），JSON 可读可手改、无需编译型依赖、无安装失败风险；后续可平滑换成 SQLite（仓储层已隔离） |
| 进程管理 | `child_process.spawn(detached)` + `taskkill /T /F` | 原生能力，启动后脱离工作台进程存活；按进程树停止，避免残留子进程 |
| 端口检测 | PowerShell `Get-NetTCPConnection`（回退 `netstat -ano`）+ `tasklist`/`Get-Process` | 检测的是**真实监听状态与占用进程**，不是数据库里的记录 |
| 实时日志 | SSE（`text/event-stream`）+ 定时轮询文件增量 | 无需 WebSocket 依赖，浏览器原生支持 |
| 启动方式 | `start.bat` / `npm run dev` | 一个命令即可跑起来 |

运行环境：Windows 10/11 + Node.js ≥ 18（当前机器 Node v24.16.0 / npm 12.0.2）。

## 5. 关键实现要点（Windows 优先）

1. **端口是"事实"不是"记录"**：每次请求都按需扫描真实监听表，项目卡片上的「运行中/已停止」由端口监听状态 + 追踪 PID 共同判定；端口被**其他进程**占用时明确标红提示冲突。
2. **启动**：按项目目录 + 启动命令以 `detached` 方式拉起，标准输出/错误重定向到 `data/logs/<id>.log`；启动后 1.2 秒回查端口，立即告诉用户成功或失败原因。
   - 实现细节：Windows 上 `shell: true` + `detached: true` 直接 spawn 时，子进程输出**不会**写进继承的文件句柄（实测），而 `detached: false` 又会让项目跟着工作台控制台一起收到 Ctrl+C。
     因此改为用自带的 `services/projectLauncher.mjs` 启动：启动器本身 detached（独立进程组，工作台退出或 Ctrl+C 都不影响项目），
     它在内部用 shell + 文件句柄跑真实命令，日志捕获可靠；启动器还会把 PID、退出码一并写进日志，便于排查。
     工作台跟踪的 PID 是启动器，视图里的 PID 仍是监听端口的真实进程（父进程链校验保证归属正确）。
3. **停止**：优先按记录的 PID 结束整棵进程树（`taskkill /T /F`），并兜底结束占用该项目端口的所有 PID；结束后校验端口是否真正释放。
4. **重启** = 停止 → 等端口释放（最多 10 秒）→ 启动。
5. **数据写入原子化**：先写 `<file>.tmp` 再 `rename`，断电/崩溃不会破坏 JSON。
6. **所有时间与路径**：后端统一输出 ISO 时间与 Windows 反斜杠路径，前端只做展示（复制路径、跳转）。

## 8. 第二阶段：SSH 只读监控

在 `serverService` 基础上新增三个模块，分层不变（services / routes / store）：

| 模块 | 职责 |
| --- | --- |
| `services/sshClient.js` | ssh2 连接封装：认证配置组装、只读命令执行、SFTP 读文件尾部、错误翻译（超时/认证失败/DNS/拒绝/不可达） |
| `services/sshMetrics.js` | 常量采集脚本（多级回退）+ 解析器（系统/uptime/负载/CPU/内存/磁盘/监听端口）+ 端口核对算法 |
| `services/serverMonitor.js` | 编排：并发闸门（默认 3）、同服务器任务去重、结果落库、白名单日志读取 |
| `utils/limiter.js` | 并发闸门 |
| `utils/secrets.js` | 密码/口令解析：环境变量 → `data/secrets.json`，**绝不落库** |

### 采集脚本（唯一被执行的命令）

```sh
echo "@@S:hostname"; hostname || cat /proc/sys/kernel/hostname
echo "@@S:user";     id -un || whoami
echo "@@S:os";       (. /etc/os-release && printf '%s\n' "$PRETTY_NAME") || uname -sr
echo "@@S:kernel";   uname -sr
echo "@@S:arch";     uname -m
echo "@@S:uptime";   cut -d" " -f1 /proc/uptime || uptime
echo "@@S:load";     cat /proc/loadavg || uptime
echo "@@S:cores";    nproc || getconf _NPROCESSORS_ONLN || echo 0
echo "@@S:cpu1";     head -n 1 /proc/stat;  sleep 1;  echo "@@S:cpu2"; head -n 1 /proc/stat
echo "@@S:mem";      free -b || cat /proc/meminfo
echo "@@S:disk";     df -PT -B1 || df -P -B1 || df -Pk /
echo "@@S:ports";    (ss -lntup) || (netstat -lntup || netstat -lnt)
echo "@@S:end"
```

- 命令是**常量字符串**，不拼接任何来自前端或数据库的内容 → 结构上不存在任意命令执行；
- 全部为读取类命令，每项都有回退（老系统没有 `ss`/`free -b`/`df -T` 也能用）；
- `@@S:` 分段解析，任何一段失败不影响其它段。

### 端口核对算法

1. `ss -lntup` 结果按端口收敛（同一端口可能有多条 tcp/udp、`0.0.0.0`/`127.0.0.1` 记录，优先保留对外监听的那条）；
2. 与 `apps[].port` 比对得到三类状态：`ok` / `recordedNotListening` / `listeningNotRecorded`；
3. 结果写回 `servers.json` 的 `portAudit`，并同步到全局端口映射表（未登记端口以 `监听中（未登记）` 出现在端口页）。

### 只读约束怎么落地

| 约束 | 实现 |
| --- | --- |
| 不执行任意命令 | 采集脚本是常量；日志读取走 SFTP，不拼 shell |
| 密码/私钥不入库 | `sanitizeServerInput` 检测到 `password`/`privateKey` 等字段直接 400；凭据只在连接瞬间从环境变量或 `data/secrets.json` 解析 |
| 日志只能读白名单 | 请求路径必须 `∈ server.logPaths`，且通过 `isSafeRemotePath`（绝对路径、无 shell 元字符），否则 403 |
| 连接不滥用 | 并发闸门（默认 3）+ 同服务器任务去重 + 结果缓存（默认 30 秒 / 页面 60 秒）+ `connectTimeout` 约束 |
| 失败可解释 | 错误码 `TIMEOUT` / `AUTH_FAILED` / `DNS_FAILED` / `REFUSED` / `UNREACHABLE` / `NO_CREDENTIAL` / `KEY_NOT_FOUND`，全部转成中文提示并写入事件日志 |

## 9. 第三阶段：Docker 容器只读监控

复用第二阶段的 SSH 通道，新增一个采集模块，分层不变：

| 模块 | 职责 |
| --- | --- |
| `services/dockerMetrics.js` | 常量 Docker 查询脚本 + 解析器（容器/镜像/端口映射/健康/资源）+ 容器与 APP 的三类核对 |

| `services/dashboardService.js` | 首页容器统计（运行/停止/异常/镜像/CPU 与内存合计）与 TOP 容器列表 |

### 采集脚本（唯一被执行的 Docker 命令）

```sh
echo "@@D:docker";  (command -v docker >/dev/null 2>&1 && echo yes) || echo no
echo "@@D:daemon";  docker info --format '{{.ServerVersion}}|{{.Containers}}|{{.ContainersRunning}}|…' 2>&1 | head -n 3
echo "@@D:version"; docker version --format '{{.Server.Version}}' || docker --version
echo "@@D:ps";      docker ps -a --no-trunc --format '{{.ID}}|{{.Names}}|{{.Image}}|{{.State}}|{{.Status}}|{{.Ports}}|{{.RunningFor}}|{{.Labels}}'
echo "@@D:inspect"; docker inspect --format '{{.Id}}|{{.Name}}|{{.State.Status}}|{{.State.StartedAt}}|{{if .State.Health}}{{.State.Health.Status}}{{else}}none{{end}}|{{.RestartCount}}|{{index .Config.Labels "com.docker.compose.project"}}|…' $(docker ps -aq | head -n 200)
echo "@@D:stats";   docker stats --no-stream --format '{{.ID}}|{{.Name}}|{{.CPUPerc}}|{{.MemUsage}}|{{.MemPerc}}|…'
echo "@@D:images";  docker images --format '{{.Repository}}:{{.Tag}}|{{.ID}}|{{.Size}}|{{.CreatedSince}}' | head -n 50
echo "@@D:end"
```

只读保证：命令是常量字符串；**没有任何** `exec` / `run` / `start` / `stop` / `restart` / `kill` / `rm` / `prune` / `build` / `pull`；`docker-parser.test.mjs` 会断言命令中不含写操作动词，`ui-snapshot.mjs` 会断言 Docker 面板里没有"重启/停止/删除"类按钮。

### 端口来源与三类核对

1. 容器发布的宿主机端口（`.Ports` 的 `0.0.0.0:8080->3000/tcp`）先按端口收敛成 `hostPort -> 容器` 映射；
2. APP 行标 `source: docker | host | unknown`，容器行附「容器名 + 镜像 + 容器内端口」；
3. 容器发布的端口若以容器状态为准（运行中 / 未运行），避免与 `ss` 视图不一致；
4. 容器与 APP 的核对：先按发布端口匹配，再按容器名 / compose service 名模糊匹配，得到 `已登记且运行 / 已登记但停止 / 容器存在但未登记`；

### 只读与安全边界

- 扫描只调用查询类 PowerShell（`Get-CimInstance Win32_Process`）与 `Get-NetTCPConnection`，加上白名单文件的 `fs` 读取；

- 项目探测最多向上 5 层、单文件最多 256KB、只读白名单文件名，杜绝全盘递归；
- AI 是可选层：未配置 `DSM_AI_API_KEY`/`DSM_AI_MODEL` 时完全跳过；配置后也只发送已采集元数据、只接收建议字段。

### 指纹与提醒

- 指纹 = `sha1(进程名|exe|项目目录|端口)` 前 16 位，**与 PID 无关**，所以重启服务后仍是同一个服务；
- 忽略后按指纹屏蔽，可恢复；"新发现提醒"记录在 `acknowledged` 里，已读后不再重复提示；
- 扫描时机：服务启动后 2.5 秒自动一次（`DSM_DISCOVERY_ON_STARTUP=0` 可关），其余由用户手动触发。

### 聚合算法（只用事实，禁止按名称合并）

```text
for 每个监听候选（已过滤的系统进程除外）:
  if candidate.projectDir 非空:
     归一化(projectDir) -> 目录桶            # 大小写/分隔符/尾部斜杠统一
  else:
     "pid:<pid>" -> 无目录桶                 # 同一进程的多个端口
for 每个已登记项目:
  if 项目的 dir 命中某个目录桶: 合并进该组（未监听的声明端口作为"仅记录"子服务）
  else: 单独成组（全部停止），仍会显示在项目页
系统/非开发进程 -> system 桶（不参与聚合）
```

- **事实字段**（pid/port/address/processName/exePath/commandLine/startedAt）在 `toService()` 里逐字段拷贝，聚合不改写、不覆盖；原始候选对象以 `service.candidate` 保留，便于溯源；
- **声明端口集合** = 项目主端口 + `project.services[].port`；子服务 `isNewSubService = 有已登记项目 && 端口不在声明集合`；
- **整体状态**：冲突（同组同端口多监听者 / 声明端口被别的目录占用）> 全部运行（全部在监听）> 部分运行（部分在监听）> 全部停止（一个都没监听）；
- **已登记匹配**：端口命中声明端口 → `registered`；只是落在项目目录下但端口没登记 → 保持 `unregistered`（在项目下标记"发现新的子服务"），用户忽略后也不会被自动"洗白"。

### 去抖算法：状态指纹，而不是时间片

```text
signature = status | port | conflictKey        # PID 故意不参与：进程重启不算一次状态变化
第一次看到某个 key  -> 只写 states，不产生事件（否则启动瞬间会把现状全当成"刚刚变化"）
signature 未变化    -> 直接跳过，一个字节都不写
signature 变化      -> 由 (previous.status -> status) 查转移表得到事件类型，commit(事件 + 新指纹)
例外：冲突 key 只在"确实冲突"时存在，第一次看到就发 port_conflict，描述变了发 port_changed
```

状态转移表（节选）：`stopped→running = started`、`running→stopped = stopped`、`running→error = crashed`、`error/冲突→running = recovered`、`port 变化而 status 不变 = port_changed`。

SSH/Docker 走同一思路：`serverMonitor.probeOnce` 成功与失败两条路径都调 `observeServerMonitor`，在线状态用 `ssh_online/ssh_offline`，容器集合用 `{name,state,health}` 逐项 diff 出 `docker_changed`（新增/移除/状态变化写进 `detail`）。

### 事实字段（每条事件都尽量带全）

`id` / `at`（ISO）/ `type` / `level`（info·warn·error）/ `source`（action·observe·discovery·ssh）/ `projectId`·`projectName` / `serviceId`·`serviceName` / `serverId`·`serverName` / `port` / `pid` / `processName` / `address` / `status`·`previousStatus` / `code`（退出码）/ `message` / `detail`。
`buildEvent` 只接受白名单字段并钳制长度（message 400、detail 300 等），`level` 走 `LEVELS` 校验，未知类型直接丢弃——外部输入不会被原样写进 JSON。

## 13. 第七阶段：按项目聚合资源占用

目标：把第二/三阶段已经采到的 **SSH 系统指标**与 **Docker 容器指标**，按项目组归集到一处，
让「这个项目一共占了多少 CPU / 内存」在项目卡片里直接看得见。

### 三条硬规则

```text
1. 只归集**已有采集结果**：没有 metrics 也没有容器的服务器一律不参与（宁可少，不可编）
2. 自动关联**只看端口**：本地 projectDir（Windows 路径）和远程 deployPath（Linux 路径）不可比；
   容器名 / compose 名属于"按名字猜"，与第五阶段"禁止按名称模糊合并"冲突 —— 都不做自动关联
3. 系统级 CPU/内存/磁盘属于**整台机器**，不算到任何项目头上（否则就是虚构归因），只作参照单列
```

端口对不上、但确实相关联时，由用户在项目上手工登记 `remoteLinks`（`{ serverId, appId?, containerName?, note }`）——
这是**记录下来的事实**，不是猜测。

### 新增模块

| 模块 | 职责 |
| --- | --- |
| `services/projectResource.js` | 纯函数归集：`groupPorts` / `linkServerToGroup` / `aggregateProjectResources` |
| `services/localDiscoveryService.js` | `getProjectGroups({ withResources })` 附上 `group.project` 与 `group.resources`；`setProjectRemoteLink` 维护显式关联 |
| `utils/validation.js` | `sanitizeRemoteLinks`：只接受"指向已有记录的 ID 引用"，不接受任意字符串 |
| `routes/discovery.js` | `POST /api/discovery/project-link` |
| `web/src/components/ProjectResources.jsx` | 资源面板：容器表 + 整机参照 + 未关联提示 + 关联入口 |
| `web/src/styles/resources.css` | 面板样式 |

### 关联与归集算法

```text
ports = 项目主端口 + project.services[].port + 分组里 live 的子服务端口
for 服务器 in "采集过"的服务器:
  容器:  published 端口 ∩ ports 非空            -> 自动关联（依据：端口一致）
         或 remoteLinks 命中该容器名            -> 显式关联（依据：手工登记）
  APP:   app.port ∈ ports                      -> 自动关联
         或 remoteLinks 命中该 appId           -> 显式关联
  只要有容器或 APP 命中（或只登记了 serverId） -> 该机进入本项目的服务器列表
totals = Σ(运行中容器的 cpuPercent / memoryUsedBytes)      # 整机指标不参与求和
未命中但采集过的服务器 -> unlinkedServers（附"为什么没关联"）
```

    "serverId": "srv_x", "serverName": "Demo", "online": true, "basis": "端口一致",
    "apps": [{ "appId": "app_x", "appName": "Dify Web", "port": 8080, "basis": "端口一致", "auto": true }],
    "system": { "scope": "system", "note": "整机指标，不计入项目合计",
                "cpuUsagePercent": 49.4, "memoryUsedPercent": 37.8,
                "memoryTotalBytes": 16777216, "memoryUsedBytes": 8388608,

## 14. 第七阶段·第二轮：SSH 后台自动采集

### 与「页面轮询」的区别

| | 页面轮询（已有） | 后台自动采集（本轮） |
| --- | --- | --- |
| 驱动方 | 前端 `usePolling` | 后端 `setInterval` |
| 关闭页面 | 停止 | 继续跑 |
| 重启进程 | 需重新打开 | 读 `data/monitor.json` 自动恢复 |
| 反复失败 | 每次都重试 | **熔断退避** |

### 熔断退避算法

```text
recordOutcome(serverId, ok):
  成功 -> failures = 0, retryAfter = null                 # 复位
  失败 -> failures += 1
          failures <= 2 : retryAfter = null               # 未达阈值，正常重试
          failures >  2 : retryAfter = now + min(30min, 1min * 2^(failures-3))

runRound():
  targets = 未关闭监控 且 未处于退避期 的服务器
  并发交给 serverMonitor 既有的 limiter(DSM_SSH_CONCURRENCY) + inFlight 同机去重
  整轮 90 秒硬超时；ticking 标志防止上一轮没跑完就重入
```

退避只在**自动**路径生效：用户手动点某台机器的「SSH 检测」，成功即 `clearFailure` 复位，
失败也记进熔断（说明确实连不上）。删除服务器时 `forgetServer` 清掉 health 条目，避免表无限增长。
定时器一律 `unref()`，调度器内部全量 catch —— **记录与采集失败绝不影响启停 / 扫描 / 采集主流程**。

### 一个必须记住的并发坑

`jsonStore.mutate(fn)` 的实现是：

```text
current  = await load()                 # 立刻读
snapshot = structuredClone(current)     # 立刻克隆
result   = await fn(snapshot)           # 修改
await queueWrite(snapshot)              # 只有"写盘"进了串行队列
```

也就是**它只串行化写盘，不串行化"读-改-写"**。一轮里 3~4 台机器并行 `recordOutcome` 时，
它们基于同一份旧快照各自 `failures+1`，最后写入者覆盖前面的：实测 8 台并行失败只记到 1 次，
该熔断的机器永远熔不断（表现为"3 台失败却只熔断 2 台"）。

修法：给 `monitorRepo` 加一条私有 Promise 链，把整个读-改-写串行化：

```js
let queue = Promise.resolve()
function serialize(task) {
  const run = queue.then(task, task)
  queue = run.then(() => undefined, () => undefined)   // 一次报错不能卡死整条链
  return run
}
```

回归测试（`auto-monitor.test.mjs` 第 10 节）**故意并行**调用 8 台 / 同一台 12 次并断言计数精确；
把 `serialize` 改成直通后这 4 项立刻失败 —— 证明测试真能守住这个坑，而不是摆设。

### 测试策略（第二轮）

- `server/test/auto-monitor.test.mjs`（56 项）：退避时长阶梯与封顶、`isCircuitOpen` 边界、
  目标筛选（关闭监控 / 熔断中 / 退避到期恢复）、设置钳制与非法值回退、成败记录与复位、
  **反复失败后不再产生新日志（日志不被刷爆）**、`resetCircuit` 立即重试、启停与改间隔、
  一轮未结束不重入、无服务器时安全、**并发不丢计数**；
- 实机验证：30 秒间隔连跑 4 轮，3 台占位机器全部进入熔断（failures 3~4），每轮 `probed=1 ok=1`，
  日志仅新增 4 行且全为成功记录。

## 15. 第七阶段·第三轮：资源历史趋势

目标：把第二轮持续采集到的水位变成"什么时候高过"的趋势，同时**不违反本项目"不编数据"的一贯口径**。

### 新增模块

| 模块 | 职责 |
| --- | --- |
| `store/resourceStore.js` | `data/resources.json`：按服务器分桶的环形采样 + 尖峰告警列表 |
| `services/resourceHistory.js` | `extractSample` / `recordSample`（去抖）/ `detectSpikes`（冷却）/ `buildSeries`（断档与统计） |
| `utils/serialQueue.js` | 通用的"读-改-写"串行化（第二轮教训抽出复用） |
| `web/src/components/Sparkline.jsx` | 真实数据趋势线 + 统计摘要 |
| `web/src/components/ResourceTrend.jsx` | 概览页趋势面板（窗口切换 / 断档提示 / 尖峰列表） |

### 为什么尖峰不进 events.json

第六阶段的 `events.json` 语义是**服务生命周期变化**（启动 / 停止 / 崩溃 / 恢复 / 冲突 / 上下线 / Docker 变化），
且 `events-e2e.test.mjs` 硬断言"十种事件类型"。CPU 高不是生命周期变化，硬塞第 11 种类型会：

1. 破坏既有契约与 CI；2. 让时间线变成"什么都能往里扔"的杂物箱。

所以资源告警独立存 `resources.json`，画在自己的趋势面板上。

### 三条不编数据的实现细节

```text
① 失败不记点
   setSshMonitor 在采集失败时保留上一次的 metrics（metrics ?? server.metrics）
   → 若失败路径也记历史，趋势图会出现"旧值反复出现"的假稳定
   → recordSample 只挂在 probeOnce 的成功 return 之前；catch 分支不记
   → 回归测试用真实失败链路（连一台必然不通的 SSH）断言点数不变

② 断档不插值
   buildSeries 计算相邻采样间隔中位数，超过 3 倍视为断档，返回 gaps[{from,to,ms}]
   前端 x 轴按【原始采样槽位】定位（不是"该指标第几个有效点"的下标）
   → 某项指标中间缺采样时，线段在空洞处切断，而不是连成直线假装时间均匀

③ 点不够不画
   有效点 < 2 → 显示"采样点不足，暂不绘制趋势"，绝不画一条假直线冒充趋势
```

### 去抖与容量

| 项 | 默认 | 环境变量 |
| --- | --- | --- |
| 两次采样最小间隔 | 30 秒 | `DSM_RESOURCE_MIN_GAP_MS` |
| 每台机器保留点数 | 720（2 分钟间隔 ≈ 24 小时） | `DSM_RESOURCE_MAX_SAMPLES` |
| CPU 尖峰阈值 | 85% | `DSM_RESOURCE_SPIKE_CPU` |
| 内存尖峰阈值 | 90% | `DSM_RESOURCE_SPIKE_MEM` |
| 同指标告警冷却 | 15 分钟 | `DSM_RESOURCE_SPIKE_COOLDOWN_MS` |

### 本轮修掉的三个坑

1. **`numberOrNull` 把"没采到"变成 0**：`Number(null)===0`、`Number('')===0`，会把缺失值画成 0% 的假低谷。改为显式判 null/undefined/空串/布尔。
2. **尖峰冷却误判"从未告警"**：`lastAt=0` 参与 `now - lastAt` 等于拿纪元时间做差，首次告警被吞。改为无记录时直接放行。
3. **趋势线 x 轴假装时间均匀**：按过滤后下标定位会把空洞连成直线。改为按原始采样槽位定位并切断。

### 测试策略（第三轮）

- `server/test/resource-history.test.mjs`（77 项）：`parseWindow` 各种写法与非法值、
  `extractSample`（根分区优先 "/"、缺项为 null 而非 0）、`detectSpikes`（阈值 / 冷却 / 缺值不判定 /
  跨指标互不影响）、`recordSample`（去抖 / 无数据跳过 / 缺 ID 安全 / **失败不记点的真实链路回归**）、
  `buildSeries`（断档识别 / 统计量 / stale 判定 / 空与单点安全）、
